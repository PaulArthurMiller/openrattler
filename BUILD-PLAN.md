## What We're Building

Image attachment support for OpenRattler — security-first. Images are accepted only from
channels that explicitly opt in and senders on a dedicated image allowlist, stripped at the
channel adapter if any gate check fails, and tagged with SHA-256 provenance metadata when
they pass. The main agent gains the ability to reason about image content via Anthropic's
multi-part content block format.

**Branch:** `build/image-attachments-option-a`

**Option B** (sanitization subagent, content scanning) is explicitly out of scope here.
47.1's job is: right person, right channel, right format — then pass it through cleanly.

### Why the gate lives in the channel adapter

The guard must fire before the `UniversalMessage` is built — not after. If the image bytes
reach the agent runtime, they've already crossed the trust boundary. Strip early, deliver
text regardless. This is the same philosophy as the sender allowlist: the attacker never
gets into the message bus.

### Why the image rate limiter is separate from the message rate limiter

A sender can be trusted for text messages (10/min, 60/hour) but limited on images (5/hour).
Image processing is more expensive per turn — a separate limit gives you precise control
without touching the text traffic policy.

### Why SHA-256 provenance hash

You cannot tell where an image came from after it's been base64-encoded. The `sha256` field
lets you correlate an audit log entry (`image_received`, sha256=`abc123`) to a specific
received file without storing image bytes in the log. If something suspicious surfaces later,
you can match the hash.

### Why Anthropic image format is emitted from `_build_messages()`

The runtime already builds messages in a format that the Anthropic provider understands
(system role extraction, tool result wrapping). Images follow the same pattern: emit the
Anthropic multi-part block format, the provider passes it through. The OpenAI provider
would need a converter if image support is ever needed there — that's future scope.

## Data Flow: Image Through the Gate

```
SlackAdapter._build_universal_message(raw)
  │
  ├─ extract text (existing)
  ├─ extract files[] if present (NEW)
  │     │
  │     └─ for each file:
  │          ├─ content_type, size from Slack metadata (no download yet)
  │          └─ pass to ImageAttachmentGate.check_and_fetch()
  │               │
  │               ├─ gate check 1–5 on metadata
  │               │   (download only if all pass)
  │               │
  │               ├─ PASS: GET url_private with bot_token header
  │               │        → raw bytes → base64 → sha256
  │               │        → MessageAttachment(...)
  │               │        → audit: image_received {attachment_id, sha256}
  │               │
  │               └─ FAIL: audit log rejection event + return rejection_reason
  │                        (rejection_reason appended to reply text)
  │
  └─ create_message(..., attachments=[...])  → UniversalMessage
```

**What happens to rejected images:**
The text portion of the message is always delivered. If an image was stripped, the adapter
appends a brief note to the system-level reply (e.g. "Your image was not accepted: media
type not permitted."). The channel-disabled case is silent by design — no reply.

## Piece 47.1 — Image Attachments, Option A

### Why one piece, not four

The four areas (model, config, gate, adapter, runtime) are tightly coupled — there's no
useful stopping point between them. A `MessageAttachment` model with no gate to populate
it isn't testable. A gate with no adapter to call it produces nothing. Building it as one
cohesive piece means each sub-step produces real, exercisable code that feeds the next one.

---

### Sub-step 1: MessageAttachment model + ImageAttachmentConfig

**Build in:**
- `openrattler/models/messages.py`
  - New `MessageAttachment(BaseModel)` with fields:
    `attachment_id: str`, `media_type: str`, `data: str` (base64),
    `size_bytes: int`, `sha256: str`, `origin_channel: str`,
    `declared_by_sender: str`, `received_at: datetime`
  - Add `attachments: list[MessageAttachment] = Field(default_factory=list)` to `UniversalMessage`
  - Update `create_message()` factory: add `attachments: Optional[list[MessageAttachment]] = None`
    parameter, passed through to the model. `create_response()` and `create_error()` do NOT
    propagate attachments — responses from the agent carry no image data.

- `openrattler/config/loader.py`
  - New `ImageAttachmentConfig(BaseModel)` with fields:
    `enabled: bool = False`,
    `sender_allowlist: list[str] = Field(default_factory=list)`,
    `max_size_bytes: int = Field(default=10_485_760, gt=0)`,
    `max_per_hour: int = Field(default=5, gt=0)`,
    `permitted_media_types: list[str] = Field(default_factory=lambda: ["image/jpeg", "image/png", "image/webp", "image/gif"])`
  - New module-level helper `parse_image_attachment_config(settings: dict[str, Any]) -> ImageAttachmentConfig`
    that extracts `settings.get("image_attachments", {})` and constructs the model.
    This keeps the generic `ChannelConfig.settings: dict[str, Any]` shape unchanged.

**Tests:**
- `tests/test_models/test_messages.py` — MessageAttachment round-trip; UniversalMessage with/without attachments; `create_message()` with attachments; `create_response()` does NOT propagate attachments
- `tests/test_config/test_loader.py` — ImageAttachmentConfig defaults; `enabled=False` default; parse helper from full dict; parse helper from empty dict (all defaults); `max_size_bytes` must be positive

**Why first:** These are the shared types that every other sub-step depends on. If the shape of `MessageAttachment` needs adjustment, better to catch it before the gate and adapter code are built around it.

### Sub-step 2: ImageAttachmentGate

**Build in:**
- `openrattler/security/image_gate.py` — NEW file

```
class ImageAttachmentGate:
    """Security gate for image attachments.

    Checks each candidate image against five ordered conditions.
    Any failure strips the image and continues with text-only delivery.
    All events (pass and fail) are written to the audit log.
    """

    __init__(config: ImageAttachmentConfig, audit: Optional[AuditLog] = None)
        → also creates a per-instance RateLimiter(max_per_minute=1_000_000, max_per_hour=config.max_per_hour)
          (the per-minute cap is effectively unlimited; only the hourly cap matters)

    async def check_metadata(
        sender_id: str,
        channel: str,
        content_type: str,
        size_bytes: int,
    ) -> Optional[str]:
        """Run checks 1–5 against metadata (before downloading bytes).

        Returns None if all checks pass, or a human-readable rejection reason string.
        Writes the appropriate audit event regardless.
        """

    async def build_attachment(
        sender_id: str,
        channel: str,
        content_type: str,
        raw_bytes: bytes,
    ) -> MessageAttachment:
        """Given raw bytes that already passed check_metadata, build the MessageAttachment.

        Records the image_received audit event with sha256 and attachment_id.
        """
```

**Gate check order (in `check_metadata`):**
1. `config.enabled` — `False` → audit `image_attachment_disabled`, return reason `None`
   (silent — no rejection message to the user for this case)
2. `sender_id in config.sender_allowlist` — not in list → audit `image_sender_rejected`, return reason string
3. `content_type in config.permitted_media_types` — not permitted → audit `image_type_rejected`, return reason string
4. `size_bytes <= config.max_size_bytes` — too large → audit `image_size_rejected`, return reason string
5. `await rate_limiter.check(sender_id)` — over limit → audit `image_rate_limited`, return reason string

On pass: `await rate_limiter.record(sender_id)` — record the accepted image.

**Why `check_metadata` and `build_attachment` are separate:** We run the gate on Slack metadata
before downloading bytes. If any check fails, we never touch Slack's CDN. The download only
happens if all five checks pass. This two-step split makes testing straightforward — you can
unit-test all rejection conditions without mocking HTTP.

**Audit events summary:**

| Event | When |
|---|---|
| `image_attachment_disabled` | Channel has `enabled=false` |
| `image_sender_rejected` | Sender not in image_allowlist |
| `image_type_rejected` | Media type not in permitted list |
| `image_size_rejected` | File exceeds max_size_bytes |
| `image_rate_limited` | Sender over hourly limit |
| `image_received` | All checks passed; includes `attachment_id` + `sha256` |

**Tests (`tests/test_security/test_image_gate.py`):**
- `check_metadata` returns rejection reason for each of the 5 failure conditions
- Each failure logs the correct audit event
- `check_metadata` returns `None` when all checks pass
- `build_attachment` returns a valid `MessageAttachment` with correct sha256
- `build_attachment` records the `image_received` audit event with sha256
- Rate limiter: 5th image in an hour passes, 6th is rejected
- `enabled=False` is silent (no reason string returned, no user-facing rejection)
- Empty sender allowlist blocks all senders

### Sub-step 3: Slack adapter image extraction

**Build in:**
- `openrattler/channels/slack_adapter.py`

**Changes:**
- In `__init__`:
  - Parse `ImageAttachmentConfig` via `parse_image_attachment_config(settings)`
  - Instantiate `ImageAttachmentGate(config=self._image_config, audit=self._audit)`
  - Store as `self._image_gate: ImageAttachmentGate`

- In `_build_universal_message()` (or wherever the UM is assembled):
  - Extract `raw.get("files", [])` from the Slack event
  - For each file:
    1. Call `await self._image_gate.check_metadata(sender_id, "slack", file["mimetype"], file["size"])`
    2. If rejected: append rejection reason to `_rejection_notes` list
    3. If passes: download `file["url_private"]` using `self._session.get(url)` (bot token is already in the session's Authorization header) → `raw_bytes`
    4. Call `await self._image_gate.build_attachment(sender_id, "slack", file["mimetype"], raw_bytes)`
    5. Append to `attachments` list
  - If `_rejection_notes` is non-empty, append the rejection reasons to the text content
    (e.g. `"\n[Image not accepted: media type not permitted]"`). Text message still delivers.
  - Pass `attachments=attachments` to `create_message()`

**New constant:** `_REQUIRED_IMAGE_SETTINGS` is empty — `image_attachments` is optional;
the gate defaults to `enabled=False` if the key is absent from settings.

**Tests (`tests/test_channels/test_slack_adapter.py`):**
- Valid image: UM has one `MessageAttachment`, text content unchanged
- Each rejection condition: UM has no attachments, rejection note in params["content"]
- `enabled=False` (default): UM has no attachments, text is unchanged (silent)
- Empty sender allowlist: UM has no attachments, rejection note in text
- Text-only message (no `files` key): UM has no attachments (regression — existing behavior)
- Multiple files: both processed independently; one pass + one reject produces one attachment + one rejection note

### Sub-step 4: Runtime and provider — multi-part content blocks

**Build in:**
- `openrattler/agents/runtime.py` — update `_build_messages()`

**Current behavior (text-only):**
```python
content = msg.params.get("content", "")
if msg.channel:
    content = f"[Channel: {msg.channel}]\n{content}"
messages.append({"role": "user", "content": content})
```

**New behavior (with attachments):**
```python
content = msg.params.get("content", "")
if msg.attachments:
    # Prepend standing note to text so the agent knows this image is verified.
    note = "[Verified image — submitted by trusted sender via trusted channel]\n"
    full_text = f"[Channel: {msg.channel}]\n{note}{content}" if msg.channel else f"{note}{content}"
    content_blocks: list[dict[str, Any]] = [
        {
            "type": "image",
            "source": {
                "type": "base64",
                "media_type": att.media_type,
                "data": att.data,
            },
        }
        for att in msg.attachments
    ]
    content_blocks.append({"type": "text", "text": full_text})
    messages.append({"role": "user", "content": content_blocks})
else:
    if msg.channel:
        content = f"[Channel: {msg.channel}]\n{content}"
    messages.append({"role": "user", "content": content})
```

Images come before the text block — this is Anthropic's recommended order for image+text prompts.

## Edge Cases and Risks

### Slack Files API — private URL download

Slack file attachments use `url_private`, which requires the bot token for download. The
bot token is already in the `aiohttp.ClientSession` Authorization header from `connect()`.
A `GET url_private` with that header will work.

⚠ **Risk:** Slack may revoke or expire the `url_private` between event receipt and download.
**Plan:** Wrap the download in a try/except; if it fails, treat as a gate rejection with
`image_download_failed` audit event and strip the attachment. Text still delivers.

### Size limit and Slack metadata accuracy

Slack provides `size` in bytes in the file object metadata. This is the raw file size before
any server-side processing. Treat it as authoritative for the size gate check.

⚠ **Risk:** `size` field absent in some Slack event payloads (rare).
**Plan:** If `size` is missing, treat as 0 (passes the size check) and let the actual download
produce the real size. Log a warning but do not block.

### `_convert_messages()` list content — existing tool result path

Tool results in `assistant` turns already use list content blocks (`tool_result` type). The
`user` role branch doesn't currently handle lists, but the `converted.append({"role": "user", "content": content})` line will pass the list through as-is — Anthropic's API accepts this.
Confirm with a test. No code change should be needed in the provider.

### Rate limiter resets on restart

`RateLimiter` is in-memory. An image rate limit resets when the process restarts.
This is the same behavior as the existing message rate limiter — acceptable for current threat model.

### OpenAI provider

The `OpenAIProvider` also calls `_convert_messages()`. If images are passed to it, the
Anthropic-format image blocks will be forwarded as-is — OpenAI uses a different format
(`image_url` with `data:` URL). The OpenAI provider is not in primary use; leave this as
a known gap noted in code comments. Do not add an OpenAI converter in 47.1.

## What Option B (47.2+) Would Add

The gate (47.1) decides whether an image is allowed in. Option B adds a layer that decides
whether the *content* of an allowed image is safe to process:

- A sanitization subagent reviews the image before it reaches the main agent
- Structured extraction schemas (e.g. "extract only the calendar event shown")
- NSFW / policy screening
- Image storage for audit replay

These are future layers. 47.1's gate is the prerequisite for all of them.
