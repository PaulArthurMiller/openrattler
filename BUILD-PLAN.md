## What We're Building

An action approval gate that sits between an agent's *intent to act* and *execution*. Currently the system has a binary `requires_approval: bool` flag on each tool. This plan replaces it with a five-level severity spectrum, adds non-bypassable dead stops, integrates with the existing security profiles, time-bounds approval tokens against replay, and routes approval requests to the right channel (CLI, Slack, or email) with rationale displayed independently of the action description.

## System Architecture

```
  Agent wants to call a tool
           │
           ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ToolExecutor.execute()                                     │
  │                                                             │
  │  1. Look up ToolDefinition → get action_level (1–5)        │
  │  2. Check DEAD_STOP_ACTIONS ──► DeadStopError (never runs) │
  │  3. Check ApprovalThresholdPolicy.requires_approval(level) │
  │     │                                                       │
  │     ├─ No  ──► Execute directly                            │
  │     │                                                       │
  │     └─ Yes ──► build ApprovalRequest (with level,          │
  │                 rationale, trace_id, token)                 │
  │                 │                                           │
  │                 ▼                                           │
  │          ApprovalManager.request_approval()                 │
  │                 │                                           │
  │          fires handler (background task)                    │
  │          awaits asyncio.Event with timeout                  │
  │                 │                                           │
  │          ┌──────┴──────────────────┐                       │
  │          │ ApprovalHandlerRouter   │                       │
  │          │                         │                       │
  │          │  CLI ─► CLIApproval     │                       │
  │          │  Slack ─► SlackApproval │                       │
  │          │  Email ─► EmailApproval │                       │
  │          └──────────────────────── ┘                       │
  │                 │                                           │
  │     ┌───────────┴──────────┐                               │
  │     │                      │                               │
  │   Approved             Denied / Timeout                    │
  │     │                      │                               │
  │  Verify token          Block execution                     │
  │  not expired               │                               │
  │     │                 Audit log denial                     │
  │  Execute tool              │                               │
  │  Audit log approval        ▼                               │
  │  (single-use token      Return ToolResult(error)           │
  │   consumed)                                                 │
  └─────────────────────────────────────────────────────────────┘
```

### Why the dead stop check is separate from the threshold

The threshold is a policy dial — users can tune it, and a compromised config could theoretically lower it. Dead stops are code — a `frozenset[str]` compiled into the binary that no config key can override. The dead stop check runs before the policy check so there is no code path that bypasses it. This is the same design principle as `AUTHORIZED_SPAWNERS` in `creator_validator.py`.

### Why rationale is displayed independently

An agent could craft a rationale that visually overshadows the action description ("Just tidying up some files — safe to approve" when the action is `delete_workspace`). The handler templates print **Action** and **Rationale** in separate, clearly-labeled blocks, in that order. The action always comes first, so the user reads *what* before they read *why*.

### Piece 39.1 — Action Level Model + Dead Stop Registry

**Build:**
- Create `openrattler/security/action_levels.py` with:
  - `ACTION_LEVEL_DESCRIPTIONS: dict[int, str]` — human-readable label for each level (e.g. `{1: "Permanent, irreversible, or financial cost", ...}`)
  - `DEAD_STOP_ACTIONS: frozenset[str]` — hardcoded set of action names that may never execute (e.g. `"force_push_main"`, `"drop_table"`, `"rm_workspace_recursive"`). This is a frozenset in code, not a config key.
  - `DeadStopError(action: str)` exception — raised when a dead-stop action is attempted; carries the action name for audit logging
- Add `action_level: int = 5` to `ToolDefinition` in `openrattler/models/tools.py`
  - Default is 5 (read-only/sandboxed) — safest possible default; tools must opt into lower levels explicitly
  - Keep `requires_approval: bool` as-is for backward compat for now
- Annotate every existing built-in tool in `tools/builtin/` with its correct level:
  - `channel_tools.py`: Slack send = level 2, email send = level 1
  - `file_ops.py`: file write = level 3, file delete = level 1
  - `session_tools.py`: session create = level 4
  - `memory_tools.py`: memory read = level 5, memory write = level 3, `update_heartbeat` = level 3
- Tests in `tests/test_security/test_action_levels.py`:
  - Dead stop frozenset is immutable
  - All ACTION_LEVEL_DESCRIPTIONS keys are 1–5
  - Every built-in tool has an action_level in range 1–5
  - DeadStopError carries the action name

**Why first:** The level field and registry are the foundation. Every downstream piece references them. If the level concept turns out to need adjustment (e.g. the default value, the enum shape), better to catch that before the policy and executor code depend on it.

**Done when:** `pytest`, `mypy`, `black` all pass. Every existing built-in tool has an explicit `action_level`.

### Piece 39.2 — Enhanced ApprovalRequest + Token System

**Build:**
- In `openrattler/security/approval.py`, update `ApprovalRequest`:
  - Add `action_level: int` — declared by executor, not agent
  - Add `rationale: Optional[str] = None` — agent's stated reason (displayed independently)
  - Add `trace_id: Optional[str] = None` — UM trace for cross-system correlation
  - Add `approval_token: str` — UUID generated by the executor; single-use
  - Add `token_expiry: datetime` — `now + token_lifetime_seconds` (default 5 min)
- In `ApprovalResult`, add `approval_token: str` and `token_expiry: datetime` (passed through from the request for the executor to verify)
- In `ApprovalManager`:
  - Add `_consumed_tokens: set[str]` — tokens that have already been used for execution
  - Add `consume_token(token: str, expiry: datetime) -> bool` — validates token is unused and not expired; marks it consumed; returns False (deny) if invalid. This is called by `ToolExecutor` immediately before execution, not at approval time.
  - Update `request_approval` audit event to include `action_level`, `trace_id`
  - Update `resolve` audit event to include `action_level`
- Add dead stop check to `ApprovalManager.request_approval()`:
  - If `request.operation` is in `DEAD_STOP_ACTIONS`, raise `DeadStopError` immediately (no handler is called, no event is set)
  - Log `audit: dead_stop_blocked` with full parameters before raising

**Why this order:** The enhanced request model must exist before the policy (39.3) decides whether to create one, and before the handlers (39.4) format one.

**Done when:** Tests cover token expiry (expired token → False), token replay (consumed token → False), dead stop audit log, and that rationale/trace_id/level flow through to the audit event.

### Piece 39.3 — Threshold Policy + Config Integration

**Build:**
- Create `ApprovalThresholdPolicy` in `openrattler/security/action_levels.py`:
  ```
  class ApprovalThresholdPolicy:
      threshold: int  # levels <= threshold require approval
      def requires_approval(self, level: int) -> bool
      @classmethod
      def from_security_config(cls, config: SecurityConfig) -> ApprovalThresholdPolicy
  ```
  - Profile → threshold mapping: `paranoid=5`, `standard=3`, `minimal=1`
  - If `config.approval_threshold` is set, it overrides the profile default
  - `requires_approval(level)` returns `level <= self.threshold`
- Add `approval_threshold: Optional[int] = None` to `SecurityConfig` in `openrattler/config/loader.py`
  - Valid range: 1–5; validated on load
  - None means "use profile default"
- Update `needs_approval()` in `openrattler/tools/permissions.py`:
  - New signature: `needs_approval(tool_def: ToolDefinition, policy: ApprovalThresholdPolicy) -> bool`
  - Returns `policy.requires_approval(tool_def.action_level)`
  - The old `tool_def.requires_approval: bool` field is **not removed yet** — it becomes unused/deprecated and will be cleaned up in a later piece once everything is wired

**Why this order:** The policy object must exist before the executor (39.5) can use it. Config integration is self-contained and doesn't touch the handler or executor code.

**Done when:** Tests cover all three profiles + direct threshold override + boundary cases (level exactly at threshold, level one above).

### Piece 39.4 — Handler Upgrades + Multi-Channel Routing

**Build:**
- Update `CLIApprovalHandler._print_request()` in `approval.py`:
  - Display format:
    ```
    ════════════════════════════════════════════════
    [APPROVAL REQUIRED]
      Action  : push_to_remote_branch
      Target  : origin/feat/new-feature
      Level   : 2 — Significant, hard to reverse
      Agent   : agent:main
      Session : agent:main:abc123
      Timeout : 30s
    ────────────────────────────────────────────────
      Reason (agent's stated rationale):
      "The feature branch is ready for review and
       tests are passing."
    ════════════════════════════════════════════════
    ```
  - Rationale block always renders AFTER the action block, separated by a divider
  - If `rationale` is None, print `"(no rationale provided)"`
- Add `SlackApprovalHandler` in `openrattler/channels/slack_adapter.py`:
  - Posts a Slack message with the same two-block structure (action block, then rationale block)
  - Listens for reply messages containing `approve` or `deny` (case-insensitive) from an allowlisted sender
  - On match, calls `manager.resolve()`
  - Uses existing `SlackAdapter` infrastructure (bot token, channel ID from config)
- Add `EmailApprovalHandler` in `openrattler/channels/email_adapter.py`:
  - Sends a formatted email to `default_to_address`
  - Subject: `[APPROVAL REQUIRED] {operation} — Level {level}`
  - Body: same two-block structure
  - Polls IMAP for a reply containing `approve` or `deny` in the body, from an allowlisted sender
  - Uses existing `EmailAdapter` infrastructure
- Add `ApprovalHandlerRouter` in `openrattler/security/approval.py`:
  - Constructor takes `preferred_channel: str` and a mapping `{channel_name: handler}`
  - `__call__(request, manager)` dispatches to the right handler
  - Falls back to `CLIApprovalHandler` if preferred channel is unconfigured
  - Always callable (never raises for missing channel config — falls back gracefully)

**Why this order:** Handlers are leaf components — they depend on the enhanced request model (39.2) but nothing else depends on them. They can be built and tested with a mock manager before the executor integration.

**Done when:** Tests cover correct format rendering (level label shown, rationale block separate), fallback to CLI when Slack/Email not configured, and router dispatch logic.

### Piece 39.5 — ToolExecutor + Startup Integration

**Build:**
- Update `ToolExecutor.execute()` in `openrattler/tools/executor.py`:
  - Accept `policy: ApprovalThresholdPolicy` as constructor parameter (alongside existing `approval_manager`)
  - **Step 1:** Look up `tool_def.action_level`
  - **Step 2:** Check `DEAD_STOP_ACTIONS` — if hit, log `dead_stop_blocked` audit event and return `ToolResult(error=DeadStopError message)`. Do not raise (executor contract returns ToolResult, not exceptions).
  - **Step 3:** Check `needs_approval(tool_def, policy)` — if False, execute directly (no change from current flow for below-threshold actions)
  - **Step 4:** If approval needed, build `ApprovalRequest` including:
    - `action_level` from tool def
    - `rationale` from `tool_call.rationale` if present (new optional field on ToolCall, or from `tool_call.context`)
    - `trace_id` from `tool_call.trace_id` if present
    - Fresh `approval_token = uuid4()`
    - `token_expiry = now + token_lifetime_seconds`
  - **Step 5:** `await approval_manager.request_approval(request)`
  - **Step 6:** If approved, call `approval_manager.consume_token(result.approval_token, result.token_expiry)` — if this returns False (expired or replayed), log audit event and return `ToolResult(error="Approval token expired or replayed")`
  - **Step 7:** Execute tool
- Update `openrattler/startup.py`:
  - Build `ApprovalThresholdPolicy.from_security_config(config.security)` at startup
  - Build `ApprovalHandlerRouter` based on `config.channels` (what's configured determines what's available)
  - Wire both into `ToolExecutor`
- Backward-compat note: The old `requires_approval: bool` field on `ToolDefinition` can now be formally deprecated (add a comment; removal deferred to avoid breaking any external callers that might reference it)

**Why last:** This piece closes the loop — it wires together all the components built in 39.1–39.4 and validates the end-to-end flow. Integration bugs (type mismatches, wrong wiring) show up here.

**Done when:** End-to-end integration test covers: (1) level-5 tool executes without approval prompt, (2) level-2 tool triggers approval gate, (3) dead-stop tool returns error without prompting, (4) expired token is rejected, (5) denied approval blocks execution. All existing 211+ tests still pass.

## Edge Cases & Open Questions

**39.1:**
- ? Which actions should be in `DEAD_STOP_ACTIONS` on day one? Start conservative: `force_push_main`, `drop_table`, `rm_workspace_recursive`. Add more as the tool set grows.
- ⚠ MCP tools injected at runtime don't have static `action_level` annotations — `mcp/manager.py` currently forces them to `requires_approval=True`. In 39.5, treat MCP tools with no `action_level` as level 1 (strictest safe default).

**39.2:**
- ⚠ The `_consumed_tokens` set grows unboundedly in a long-running process. Add a periodic cleanup that removes entries where `expiry < now - grace_period`. This can be a simple check at the top of `consume_token()`.
- ? `rationale` field on `ToolCall` — does it exist? Check `openrattler/models/messages.py`. If not, add it as `Optional[str] = None`.

**39.3:**
- ? Config validation: if `approval_threshold` is set to 6 or 0, should `load_config` error or clamp? Decision: error with a clear message (silent clamping hides misconfiguration).

**39.4:**
- ⚠ Slack polling for approval reply adds a loop to an existing polling system. Keep the approval poll timeout short (equal to `request.timeout_seconds`) and ensure it cancels cleanly when `manager.resolve()` is called from another path (e.g. simultaneous CLI resolve).
- ⚠ Email approval polling is inherently slow (IMAP polling interval). The default `timeout_seconds` of 30 may be too short for email; consider a per-channel timeout override or a longer default for email delivery.

**39.5:**
- ? `ToolCall` may not have a `trace_id` field today. If not, add `trace_id: Optional[str] = None` to `ToolCall` and propagate from `UniversalMessage.trace_id` at the point where `ToolCall` objects are created.
- ⚠ The old `requires_approval: bool` on `ToolDefinition` will now be ignored by the executor. Add a deprecation comment in the model. Don't remove it yet — MCP bridge references it and removal needs its own PR.

## Conventions for This Build

- `DEAD_STOP_ACTIONS` uses the same frozenset pattern as `AUTHORIZED_SPAWNERS` — compile-time constant, never read from config
- Action levels are `int`, not an `Enum`, to keep JSON serialization trivial and avoid import cycles
- The `approval_token` UUID is generated by `ToolExecutor`, not by the agent or the `ApprovalManager` — the executor owns the execution gate
- Audit events for this feature use event names: `approval_requested`, `approval_resolved`, `dead_stop_blocked`, `approval_token_rejected`
- All new handler classes follow the existing `ApprovalHandler` callable protocol: `async (request, manager) -> None`

## What We're Building

A capability for the personal assistant to invoke Claude Code
(CC) as a subprocess and use it for software development tasks — writing code, running
tests, making commits — while keeping CC's work structurally isolated from the human
user's files, repos, and personal Claude config.

The integration uses **Option A** (task-level gating): the assistant approves the task
description before spawning CC, then CC runs non-interactively within a sandboxed
workspace. A **plan review step** (adapted from Option B) runs CC in read-only mode
first to produce a plan, which becomes its own approval request before execution
begins.

## Data Flow: A Complete CC Task

```
USER (Slack): "Fix the login bug in the auth module"
       │
       ▼
The assistant formulates task description (with full conversation context)
       │
       ▼
[APPROVAL GATE — Level 3]
  Action  : cc_write_task
  Target  : {prefix}-auth-fix (new project in workspace)
  Level   : 3 — Moderate, modifies local state
  Reason  : "Fix login bug in auth module"
  Approve? [y/N]     ← human approves via configured channel
       │
       ▼
WorkspaceManager.create_project("auth-fix")
→ C:\Users\{assistant_name}\projects\{prefix}-auth-fix\
→ writes CLAUDE.md with workspace rules
→ inits git repo, sets assistant author identity, installs pre-push hook
       │
       ▼
[PLAN PHASE — read-only CC spawn]
CC: --allowedTools Read,Glob,Grep,LS
CC analyzes codebase, produces plan output (JSON)
CCPlanReviewer formats:
  "I will patch SessionValidator.verify() in auth/validator.py
   and add a regression test in tests/test_auth.py"
       │
       ▼
[PLAN APPROVAL — Level 3]
  Plan    : Patch SessionValidator.verify() + add test
  Files   : auth/validator.py, tests/test_auth.py
  Approve? [y/N]     ← auto-approved under minimal profile
       │
       ▼
[EXECUTION PHASE — full CC spawn]
CC: --allowedTools Read,Write,Bash,Glob,Grep
CC implements, tests, commits to branch {prefix}/auth-fix
Output captured as JSON → CCOutputParser
       │
       ▼
UniversalMessage(type="cc_result", content=summary, metadata={branch, commit, tokens})
→ Assistant sends to Slack: "Done. Branch {prefix}/auth-fix is ready for your review."
```

The human user controls what happens next — reviewing the branch and merging
(or not) is entirely outside the assistant's reach.

## CC-Specific Tool Definitions and Action Levels

These are the tool names exposed to the agent runtime. Action levels follow the
same 1–5 scale as all other tools.

| Tool name            | Level | Description                                          |
|----------------------|-------|------------------------------------------------------|
| `cc_read_analyze`    | 5     | Read-only CC session: code review, explanation, Q&A  |
| `cc_write_task`      | 3     | CC writes/modifies files within workspace            |
| `cc_run_with_shell`  | 2     | CC task that includes shell command execution (Bash) |
| `cc_git_commit`      | 3     | CC commits staged changes to an assistant branch     |
| `cc_git_push_branch` | 2     | CC pushes an assistant branch to remote              |
| `cc_promote_request` | 1     | Request to merge an assistant branch (always level 1)|

Dead stops — added to `DEAD_STOP_ACTIONS` (compile-time frozenset, no config override):

| Action name               | Reason                                             |
|---------------------------|----------------------------------------------------|
| `cc_bypass_permissions`   | Never pass --dangerously-skip-permissions to CC    |
| `cc_push_main`            | CC may never push directly to main                 |

Note: Path-outside-workspace violations are caught structurally by
`--add-dir` (CC-level) and `WorkspaceManager.validate_path()` (tool-level).
They do not need a named dead stop — the path fence prevents them at the
subprocess boundary.

are structured. Workspace logic is pure file I/O — no subprocess, no approval system —

### Piece 40.3 — CCSubprocessManager

**Build:**
- Create `openrattler/tools/claude_code/subprocess_mgr.py` — `CCSubprocessManager`:
  - Constructor takes `CCConfig`
  - `_active_sessions: dict[str, asyncio.subprocess.Process]` — currently running sessions
  - `_validate_args(args: list[str]) -> None` — scans for forbidden flags
    (`--dangerously-skip-permissions`, `--no-permissions`, direct `--permission-mode bypass`);
    raises `DeadStopError("cc_bypass_permissions")` if found — this is the subprocess-level
    structural check (defense in depth alongside the tool-level dead stop)
  - `spawn(task: str, project_path: Path, allowed_tools: list[str], env: dict) -> CCResult`:
    - Checks `len(_active_sessions) < max_concurrent_sessions`; raises if at limit
    - Builds argv: `[claude_binary, "-p", task, "--output-format", "json",
                    "--allowedTools", ",".join(allowed_tools), "--add-dir", str(project_path)]`
    - Calls `_validate_args(argv)` before spawning
    - Spawns with `asyncio.create_subprocess_exec`, `cwd=project_path`, merged env
    - Awaits stdout with `asyncio.wait_for(timeout=session_timeout_seconds)`
    - On timeout: kills process, removes from `_active_sessions`, returns `CCResult(error="timeout")`
    - On success: returns `CCResult(stdout=..., returncode=...)`
  - `kill_all()` — kills all active sessions (used in shutdown)
- Create `openrattler/tools/claude_code/output_parser.py` — `CCOutputParser`:
  - `parse(raw: str) -> CCParsedOutput` — parses `--output-format json` response
  - Fields extracted: `result` (text), `cost_usd`, `num_turns`, `session_id`, `error`
  - Resilient to missing fields (all optional except `result`/`error`)
- Tests in `tests/test_tools/test_cc_subprocess.py`:
  - `_validate_args` raises `DeadStopError` on `--dangerously-skip-permissions`
  - `_validate_args` raises `DeadStopError` on `--permission-mode bypass`
  - Session limit: third spawn when limit=2 raises immediately
  - Timeout: mock slow process → CCResult with error="timeout"
  - `kill_all` terminates all tracked processes
  - `CCOutputParser.parse` handles missing `cost_usd` gracefully
  - `CCOutputParser.parse` returns error field when CC exits non-zero

**Note on Windows process kill:** `asyncio.subprocess.Process.kill()` calls
`TerminateProcess` on Windows (equivalent to `SIGKILL`), which is the correct
behavior. No platform-specific handling needed here.

**Why this order:** The subprocess manager is the lowest-level component — it has no
dependency on the plan reviewer or the full tool orchestration. Building and testing it
in isolation means the most complex external-process logic is validated before it's
wrapped in the higher-level flow.

**Done when:** `pytest`, `mypy`, `black` pass. All subprocess tests pass with the CC
process mocked at the `asyncio.create_subprocess_exec` boundary. No real CC invocation
required.

## Structural Fences — Summary

Five fences in order of hardness. No single fence should be relied on alone.

| # | Fence | Type | Enforced by |
|---|-------|------|-------------|
| 1 | `--add-dir` restricts CC file access | Hard (CC-level) | CCSubprocessManager argv |
| 2 | `CLAUDE_CONFIG_DIR` isolates CC config | Hard (env) | WorkspaceManager.get_env() |
| 3 | git pre-push hook blocks push to main | Hard (git-level) | WorkspaceManager.create_project() |
| 4 | `DEAD_STOP_ACTIONS` blocks cc_bypass/cc_push_main | Hard (code) | existing ToolExecutor |
| 5 | CLAUDE.md in workspace projects | Soft (behavioral) | WorkspaceManager.write_project_claude_md() |

Defense in depth: fence ④ fires before any subprocess is spawned; fence ① fires at
the OS level even if fence ④ were somehow bypassed; fence ③ fires at push time even
if CC's working directory were somehow wrong.

## Approval Profile Behavior for CC Tools

| Profile   | Threshold | cc_read_analyze (5) | cc_write_task (3) | cc_run_with_shell (2) | cc_promote_request (1) |
|-----------|-----------|---------------------|-------------------|-----------------------|------------------------|
| paranoid  | 5         | requires approval   | requires approval | requires approval     | requires approval      |
| standard  | 3         | auto-approved       | requires approval | requires approval     | requires approval      |
| minimal   | 1         | auto-approved       | auto-approved     | auto-approved         | requires approval      |

`cc_promote_request` is always level 1 — it requires human approval under every profile.
This is the "wall" between the assistant's work and the human's main branch.

## Conventions for This Build

- The `claude_code/` module is a self-contained package. Nothing outside it should import
  from inside it except `startup.py` (which wires it) and `tools/registry.py` (which
  registers the tool definitions). No circular imports with the approval or security modules.
- CC subprocess args are built as a `list[str]` and validated before spawn — never
  interpolated into a shell string (no `shell=True`). This prevents shell injection.
- All CC-initiated git commits use the workspace-local git config (author set per-repo
  in `create_project`). The `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL` env vars are also
  set in `get_env()` as a belt-and-suspenders measure.
- CC tool names in `--allowedTools` must be validated against a known-good list at startup
  (warn if an unrecognised tool name is in `exec_allowed_tools` config — likely a typo).
- Every CC session gets a UUID `session_id` logged to the audit trail (start, end, cost,
  duration). This is the correlation key if something goes wrong.
